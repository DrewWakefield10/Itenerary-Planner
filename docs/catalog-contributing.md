# Researching and maintaining places

The directory has 11 browsing groups; the itinerary planner has separate overnight bases. Palawan is a directory group, while El Nido, Coron and Puerto Princesa remain selectable bases. Metro Manila is browsed as Manila, but every accepted record stores its actual city. Never rewrite an administrative address to match a browsing label.

1. Research an actual named place through an official tourism office, local government, attraction or business website, accessible public business page, or a suitable map reference. Reuse a stable ID for an existing place. Check aliases, nearby branches, relocated venues, beach access points, and packaged-tour components before creating another record.
2. Add or update a candidate in the appropriate `lib/catalog/directory-*.json` module. Record reviewed identity and municipality separately, with the exact supporting URL and real review date. Acceptance requires both; retain rejected and unresolved candidates with an honest reason. Save incremental batches of 20–25 where possible, grouped by destination; the last destination batch may be smaller. Document the save and evidence in the matching research note.
3. Use null for unknown barangay, street address, or coordinates. A municipality source does not verify a street address or entrance pin. Reuse existing coordinate evidence and dates without upgrading their status. Sources confirming existence do not verify present access, ticket prices, opening hours, accessibility, transport duration or weather suitability.
4. Keep administrative `region`, `province`, `city_municipality`, `barangay`, and `address` separate from `destination_group`. Independent cities can have a null province; geographic associations can be explained in the record's notes. Do not infer that every Siargao attraction belongs to General Luna or that an Iloilo province attraction is in Iloilo City.
5. Map to an itinerary stop only when the existing overnight base and stop are appropriate. Keep `itinerary_base_slug` null when no reviewed overnight-base mapping exists. `catalog_stop_id` may retain an exact factual cross-reference for practical details even when no base is approved; that does not enable itinerary additions. For adding schedulable seed stops, extend `research-luzon.json`, `research-visayas.json`, or `research-islands.json`; supply a geographic cluster, conservative visit-duration estimate, visit mode, booking notes and independent fact evidence. Outlying visits use excursion/separate-base modes. A full package lists component IDs; components are not added and charged independently.
6. Entry price is separate from the illustrative planning allowance. Unknown entry price is null, never zero. Every known fee needs a unit and its own source. Hours are venue-local regular hours, not availability. Record closure/access uncertainty with manual scheduling so the generator cannot suggest a stale venue automatically.
7. Use existing licensed local images only for the place they actually depict. New images need a stable local asset, reuse license and attribution. Otherwise retain the compass fallback. Adding a directory record never adds a Wikipedia trend mapping.
8. Run `npm run export:directory`, `npm run validate:catalog`, tests and typecheck. Review generated progress and combined CSV/JSON exports. Inspect desktop/mobile Discover, combined filters, municipality search, source details, map fallback and explicit add preview. These structural checks are separate from factual source review.

Saved trips contain independent activity snapshots. Never hydrate old activities from the newest catalog or silently convert legacy `palawan` into a particular base. Add schema fields with conservative defaults; preserve source metadata through import, export, editing and acceptance. Renaming a place in a trip invalidates the relevant facts and catalog identity. Moved venues keep stable IDs where they are the same institution; explain the move and remove unsupported old pins.

Directory exports are generated static files and require no database or paid service. `public/data/lakbay-candidates.json` is the combined candidate dataset; `lakbay-locations.json` and `.csv` contain accepted records, sources and available practical seed details. `research-progress.json` and `docs/directory-progress.md` report actual counts and shortfalls. Re-run the exporter after any candidate decision changes; never hand-edit counts or generated exports.
